# 总体架构

## 1. 目标与约束

本项目处理的是多个 RimWorld Mod 同时改变同一种族时产生的组合兼容问题。上游各自单独运行可能正常，但组合后容易出现：

- 基因定义与异种生成配置不一致；
- BodyAddon 的颜色通道或着色器不匹配；
- 渲染图形在上游流程末端被重新创建，覆盖静态配置；
- 婴儿、儿童及不同朝向的耳尾位置不正确；
- 上游类型或字段变化导致硬引用失效。

架构遵守四项约束：

1. **目标收口**：只处理满足种族、部件和兼容条件的对象。
2. **静态优先、运行时兜底**：可由 Def 修正的问题不进入逐帧逻辑。
3. **反射隔离可选依赖**：上游类型不存在时应停用对应能力，而不是阻止游戏启动。
4. **缓存安全**：修改 Def 或 Pawn 状态后，必须在合适的生命周期刷新图形缓存。

## 2. 分层模型

### 2.1 静态定义修正层

在 Def 加载阶段修正稳定、声明式的数据：

- BodyAddon 的颜色来源通道；
- 需要双纹理或复杂透明度的着色器类型；
- 基因与扩展图形之间的映射关系；
- 已知身体类型和朝向的定位结构。

该层使用条件化 Add/Replace，避免假设目标节点必然存在。

### 2.2 数据协调层

同一个异种是否可用于目标种族，与它在 PawnKind 或阵营中的生成概率，是两个必须同步维护的维度：

```text
可选池 S
生成概率映射 P : Xenotype → Weight

约束：P 中所有非零项目都应属于 S；
      S 中不希望随机生成的项目可以没有非零权重。
```

具体异种名称和权重属于发行配置，本仓库不记录。

### 2.3 运行时兼容层

静态 Def 无法覆盖所有渲染路径。上游会在运行时根据 Pawn、基因或变体重新生成 Graphic，因此运行时层设置一个窄范围兜底：

1. 接收上游已经选好的最终 Graphic；
2. 判断 Pawn 是否属于目标兼容范围；
3. 判断当前节点是否为目标耳朵或尾巴；
4. 计算预期的主色与辅色；
5. 仅在颜色不一致时创建重新着色的 Graphic；
6. 任何可选依赖缺失或反射失败都返回原始结果。

这种方式保留上游对纹理路径、变体和绘制参数的选择，只修正冲突维度。

### 2.4 生命周期刷新层

修正完成后，需要让游戏丢弃旧的图形缓存。刷新时机覆盖：

- 游戏完成初始化；
- 地图载入或生成完成；
- 角色配置界面的进入与关键绘制阶段；
- Pawn 的相关基因或外观状态发生变化后。

刷新必须幂等，并避免每帧无条件遍历所有 Pawn。

## 3. 依赖适配

对可选依赖使用适配器式发现：

```text
类型发现 → 方法签名筛选 → 能力缓存 → 安全调用
    │             │              │          │
  找不到         不匹配          成功一次      异常
    └──────► 标记能力不可用并退回原行为 ◄─────┘
```

反射查找应按“类型名 + 程序集候选 + 参数/返回类型”确认目标，避免仅按方法名匹配重载。

## 4. 为什么不公开完整实现

完整实现包含针对具体上游 Mod 的 DefName、纹理路径、概率表、偏移坐标和其他可直接运行的数据。其一部分源自第三方发布包。公开这些内容会把架构说明重新变成完整材料镜像，因此本仓库只陈述模块职责、控制流和安全不变量。
